======================================================================
2. ORIGEN DEL PROYECTO
======================================================================

HMS AI Assistant nació para resolver un problema empresarial concreto:

- Correos importantes sin atender.
- Solicitudes repetidas.
- Personas esperando una respuesta.
- Tareas y compromisos olvidados.
- Pagos o trámites detenidos.
- Falta de visibilidad sobre asuntos pendientes.
- Dificultad para revisar varias bandejas.
- Exceso de mensajes promocionales o secundarios.
- Ausencia de métricas sobre tiempos de respuesta y pendientes.

El caso inicial se relacionó con una empresa de construcción en la que podían
quedar correos sin responder, solicitudes críticas y pagos detenidos, incluso
por cantidades importantes.

Desde el inicio se acordó que HMS no debía convertirse en otro cliente de
correo. Su misión debía ser actuar como una capa inteligente sobre las cuentas
existentes.

La visión original fue:

“Detectar lo que requiere atención, identificar quién espera respuesta,
convertir mensajes en tareas o casos, avisar al usuario y permitirle actuar
sin revisar manualmente cada correo.”

======================================================================
3. VISIÓN ORIGINAL DE HMS PROFESIONAL
======================================================================

HMS Profesional debe responder:

“¿Qué asunto laboral requiere atención, quién debe resolverlo y qué puede
ocurrir si no se atiende?”

La unidad principal del sistema no debe ser el correo aislado, sino el
ASUNTO OPERATIVO o CASO.

Capacidades buscadas:

- Detectar correos importantes.
- Identificar mensajes sin respuesta.
- Distinguir espera interna y espera externa.
- Detectar solicitudes.
- Extraer tareas.
- Detectar compromisos.
- Identificar fechas límite.
- Detectar pagos, facturas, documentos y autorizaciones.
- Agrupar por conversación o hilo.
- Resumir conversaciones.
- Crear estados operativos.
- Asignar responsables.
- Notificar por prioridad.
- Generar métricas.
- Conservar el acceso al mensaje original.
- Permitir varias cuentas y varios proveedores.
- Operar desde celular, tableta y computadora.
- Mantener seguridad y privacidad por usuario o espacio de trabajo.

6. PROBLEMAS TÉCNICOS RESUELTOS
======================================================================

6.1. Error de sintaxis en el clasificador

El archivo:

backend/app/services/safe_case_classifier.py

presentó un f-string incompleto alrededor de las líneas 194 y 195.

Código incorrecto:

short_text = f"{subject}
{body[:1600]}".lower()

Se corrigió para usar un salto de línea válido dentro del string.

Después de la corrección:

- El archivo compiló correctamente.
- El backend pudo iniciar.
- El proceso de Uvicorn quedó activo.

6.2. TypeScript en PushNotificationsPanel

Se detectó un error de tipos en `applicationServerKey`.

El frontend esperaba `BufferSource` y la función devolvía un
`Uint8Array<ArrayBufferLike>`.

Se corrigió utilizando el buffer como `ArrayBuffer`.

6.3. Error 404 del frontend

El error 404 estuvo relacionado con:

- URL incorrecta.
- Puerto equivocado.
- Túnel anterior de Codespaces.
- Frontend detenido o recompilado.
- Necesidad de abrir la URL actual del puerto 3000.

La URL funcional del Codespace en este punto fue:

https://stunning-potato-r45467jvg69gh5p4x-3000.app.github.dev

Se confirmó que no era necesario ejecutar algunos bloques de reparación
posteriores una vez que la aplicación volvió a cargar.

6.4. Firma GPG en Git

Al intentar crear el commit documental apareció:

“gpg failed to sign the data”
“403 Author is invalid”
“fatal: failed to write commit object”

Se resolvió desactivando la firma GPG solo en este repositorio:

commit.gpgsign=false
tag.gpgsign=false

No se cambió la configuración global de otros repositorios.

6.5. Espacios finales en Markdown

`git diff --cached --check` detectó trailing whitespace.

Los espacios fueron eliminados antes de crear el commit.

9. ESTADO DE PUSH Y VAPID
======================================================================

El frontend y backend están activos, pero Push todavía requiere cerrar la
configuración VAPID.

Variables que espera el backend:

HMS_VAPID_PUBLIC_KEY
HMS_VAPID_PRIVATE_KEY_PATH
HMS_VAPID_SUBJECT

Valor predeterminado del subject:

mailto:hmcelinfo@gmail.com

El generador:

scripts/generate_vapid_keys.py

crea:

- `.hms-secrets/vapid_private.pem`
- `.hms-secrets/push.env`

Contenido esperado de `push.env`:

- HMS_VAPID_PUBLIC_KEY
- HMS_VAPID_PRIVATE_KEY_PATH
- HMS_VAPID_SUBJECT
- HMS_AUTO_SYNC_ENABLED
- HMS_AUTO_SYNC_INTERVAL_SECONDS

Hallazgo importante:

El script utilizaba `parents[2]`, lo que podía dirigir los secretos a:

/workspaces/.hms-secrets

en lugar de:

/workspaces/hms-ai-assistant/.hms-secrets

Antes de generar nuevas llaves debe comprobarse si ya existen llaves válidas
en cualquiera de esas ubicaciones.

Nunca se debe:

- imprimir la llave privada;
- guardar la llave privada en Git;
- copiar la llave privada a documentación;
- compartirla en el chat;
- hacer commit de `.hms-secrets`.

14. PRINCIPIOS DE PRIVACIDAD FAMILIAR
======================================================================

1. Ser miembro de un hogar no concede acceso automático a todos los correos.
2. Cada cuenta conectada tiene un propietario.
3. Una alerta puede ser privada.
4. Una alerta puede compartirse con miembros seleccionados.
5. Una alerta puede compartirse con el hogar.
6. El administrador del hogar no ve automáticamente datos privados de otro adulto.
7. Finanzas, salud, viajes y seguridad requieren protección especial.
8. Los códigos 2FA no deben conservarse como contenido histórico normal.
9. Las notificaciones externas deben ocultar datos sensibles.
10. SMS y WhatsApp deben ser opcionales.
11. Toda compartición debe ser explícita.
12. Toda modificación de permisos debe quedar auditada.
13. Los menores deben recibir solo información autorizada.
14. No deben descargarse adjuntos sensibles sin necesidad.
15. El usuario debe poder eliminar o revocar datos y accesos.

25. CIERRE
======================================================================

HMS AI Assistant dejó de ser solamente un detector de correos pendientes.

Al 6 de agosto de 2026 se ha convertido conceptualmente en:

“Un sistema inteligente de control de comunicaciones que transforma correos
en asuntos accionables, detecta riesgos, controla respuestas y evita que algo
importante quede sin atender.”

La Versión 2 añade una segunda oportunidad:

“HMS Family, un asistente de seguridad, finanzas y logística del hogar que
vigila varias cuentas y avisa solo cuando algo afecta realmente a la familia.”

La prioridad vigente no cambia:

Primero estabilizar HMS Profesional.
Después construir clasificación y alertas confiables.
Luego multicuenta.
Después Microsoft 365.
A continuación realizar piloto empresarial.
Solo entonces construir HMS Family.
