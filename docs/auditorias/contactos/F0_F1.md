## Por qué F0 y F1 van en un solo PR

F1 no se puede probar sin F0: cada fila de `message_participants` y cada `contact_addresses` nace de un `AddressIdentity` de F0, y los CHECK de la migración (`address_norm` solo con `parse_status='ok'`, formato de `address_norm`) son el espejo en base de datos del contrato de F0. Separarlos dejaría a F1 sin productor de datos o a F0 sin consumidor verificable. Los límites siguen siendo revisables: F0 es un archivo (`contact_identity.py`) con su propia prueba; F1 son la migración, el repositorio, el servicio y sus pruebas.

## F0 — Interfaz de identidad (`backend/app/services/contact_identity.py`)

Contrato `AddressIdentity`:

| Campo | Significado |
|---|---|
| `address_original` | Dirección tal como llegó (sin minúsculas). Si el campo no es confiable, el campo completo. Nunca se sobrescribe. |
| `address_norm` | Clave relacional. Minúsculas, dominio IDNA, equivalencia de Gmail reutilizada de `mail_direction.normalize_address`. **Vacía** si no es `ok`. |
| `display_name` | Solo descriptivo. Nunca es identidad ni criterio de fusión. |
| `parse_status` | `ok` · `ambiguous` · `invalid` |
| `source` | `gmail_api`, `microsoft_graph`, `imap`, `gmail_imap`, `stored_sender`, `stored_recipients`, `fixture` |
| `reason`, `flags` | Motivo auditable (`multiple`, `legacy_unquoted`, `header_defects`, `no_address`, …) y banderas (`display_name_contains_address`). |

Reglas: analizador estándar `email.headerregistry`; un campo de remitente con dos o más buzones es `ambiguous` (no se elige "el primero"); sin dirección válida es `invalid`; un nombre visible con forma de dirección se conserva y se marca como indicio, nunca como identidad.

Entradas: `identity_from_header` (cabecera cruda de un remitente), `identities_from_header_list` (To/Cc/Bcc crudos), `identity_from_structured` (Graph `emailAddress` o jsonb `{name,email}`), `identities_from_structured_list`, `identity_from_stored_sender` (texto de `communication_messages.sender`).

La forma con comillas devuelve la dirección real (`x@atacante.test`) y marca `display_name_contains_address`.
- Si H01 no confía y F0 sí, F0 baja a `ambiguous` (`h01_untrusted`). Si H01 confía y F0 rechaza la dirección (p. ej. dominio literal), F0 no la acepta.

## F1 — Migración `supabase/migrations/20261127_001_contacts_v1_identity.sql`

Rollback: `supabase/rollbacks/20261127_001_contacts_v1_identity_rollback.sql`. **No aplicada en Supabase.** Solo se aplicó en un Postgres 17 local aislado (127.0.0.1, base temporal por prueba) con el arnés `backend/tests/db`.

El repositorio exige que sea un punto fijo de la normalización de F0, y el servicio canoniza lo que escribe el usuario antes de comparar con los buzones conectados.

RLS activa en las tres, sin políticas, `revoke all` a `anon`/`authenticated`, grants a `service_role` (patrón `20260801214500`). No se altera ninguna tabla existente (comprobado por prueba: columnas de todas las demás tablas idénticas antes y después del rollback).

### Por qué cada tabla y no una existente

| Tabla nueva | Existente revisada | Por qué no basta |
|---|---|---|
| `message_participants` | `communication_messages.sender/recipients/cc/bcc` | `sender` es texto ambiguo (H01) y las listas jsonb no se indexan por dirección normalizada. El original sigue en `communication_messages`; esta tabla es un índice reconstruible. |
| `contact_addresses` | `case_participants` | Es por caso (`unique (case_id, email)`), solo existe con caso y la reclasificación la borra. |
| | `organizational_patterns` | Es por dominio o patrón, no por dirección, y se borra al reclasificar. |
| | `message_watch_rules` | Es por cuenta, muere en cascada con `source_message_id` y su semántica es notificar. |
| | `message_classification_rules` | Es por cuenta y fuerza categoría sin excepción de seguridad. |
| `own_address_aliases` | `communication_accounts` | Exige un buzón OAuth/IMAP real; un alias "Enviar como" no lo es. Los buzones conectados **no** se duplican aquí. |

### Repositorio y servicio

- `contact_registry_repository.py`: todo acotado por `workspace_id`. `replace_message_participants` es idempotente (la segunda ejecución hace cero escrituras). `ensure_contact_address` crea solo la identidad (dirección normalizada y su original), con manejo de carrera `23505`. No existe ninguna vía para escribir estadísticas. `record_detected_alias` nunca pisa una decisión. `decide_alias` solo acepta `confirmed`/`rejected`.
- `contact_registry_service.py`: `contacts_v1_enabled()`, `OwnAddressBook` (buzón conectado / alias confirmado / alias detectado / alias rechazado / externo) y `record_message`. Propio = buzón conectado o alias confirmado. Un `From` confiable de un enviado que no es propio → alias `detected` (no es propio ni contacto). Rechazado → externo.
